# StaffNow Backend Audit — Findings

## CRITICAL

**1. Free credits for anyone — payment bypass**
`apps/api/src/routes/credits.ts:192-251`
`POST /credits/purchase` takes `{ packageId }` from the body and immediately adds the credits (`UPDATE credits SET balance = balance + ?`). `stripeSessionId` is optional and **never verified against Stripe**. Any logged-in user can call it in a loop and mint unlimited credits (100 credits/call with `pack_100`). The real, verified path already exists in the webhook (`billing.ts:280 handleCreditPurchase`), so this endpoint is a redundant back door.
*Impact:* direct revenue loss; all paid AI/boost features become free.

**2. Full worker PII (email, phone, CV, bio) exposed to any business account**
`apps/api/src/routes/workers.ts:592-676`
`GET /workers/discover` runs `SELECT DISTINCT wp.*, u.email, …` and returns `{ ...worker }` — only `embedding` is deleted (line 658). So every row includes `u.email`, `wp.phone`, `wp.cv_url`, `wp.cv_text`, `wp.bio`.
This contradicts the explicit GDPR gate in `GET /workers/:id` (`workers.ts:738-753`), which strips exactly those fields unless self/admin/matched. There is no plan gate and no match requirement — a free business signup can page through and harvest the contact details of every worker on the platform. Worse, the query deliberately has **no SQL LIMIT** ("φέρνουμε όλο το φιλτραρισμένο σύνολο", line 587) so the whole table is returned per request before in-memory slicing.
*Severity: critical (PII / GDPR + competitive scraping).*

**3. `POST /businesses/:id/like` is permanently broken (500 on every call)**
`apps/api/src/routes/businesses.ts:472` uses `checkSwipeLimit` as **Hono middleware**, but `middleware/subscription.ts:142` defines it as `checkSwipeLimit(db: D1Database, userId: string)`. Hono invokes it as `(c, next)`, so `db.prepare(...)` is `Context.prepare` → `TypeError` → 500, and `next()` is never reached.
*Impact:* workers can never express interest in a business; the whole business-discovery swipe flow is dead.

**4. Migrations do not match the queries — several write paths throw**
Verified against every file in `apps/api/migrations/`:

| Query | Missing in schema |
|---|---|
| `businesses.ts:584` `INSERT INTO matches (… created_at, updated_at)` | `matches` has only `matched_at` (`0006`), never altered |
| `businesses.ts:514,601,617` `swipes … target_type='business'` | `swipes` CHECK allows only `('worker','job')` (`0006`), never dropped |
| `businesses.ts:601,617` `notifications (… read, updated_at)` + `type='match'` | `notifications` has `read_at`, no `read`/`updated_at`; `type` CHECK excludes `match` (`0008`) |
| `billing.ts:354,459,508`, `lib/billing.ts:522`, `admin.ts:3524` `type='billing'/'subscription'` + `read`/`updated_at` | same |
| `matches.ts:225` `FROM worker_languages` | table is `worker_profile_languages` (`0003`) — **no such table** |
| `businesses.ts:325,330,352,357` `bp.industry`, `bp.company_size`, `bp.profile_completeness` | never exist on `business_profiles` (`0004` + all ALTERs) |

Consequences: `GET /matches/:id` returns 500 **always** (`worker_languages`); `GET /businesses/discover` 500s on `bp.profile_completeness` in ORDER BY; the worker→business match flow dies mid-write after the match+conversation rows are already inserted (`businesses.ts:582-629` has no try/catch), leaving orphaned state and a 500 to the user. `0047`'s own header comment acknowledges the `notifications.type` CHECK, so the newer call sites violating it are a known-but-unfixed drift.

**5. No migration runner / no idempotency**
`apps/api/package.json:14-17` — `db:migrate` is `for f in migrations/*.sql; do wrangler d1 execute … --file="$f"; done`. There is no `schema_migrations` table, no ordering guarantee (`0036` appears twice, `0042` twice), and `0041`/`0047`/`0058` explicitly note they will fail with "duplicate column name" on re-run. Any fresh environment or re-deploy is a coin flip.
Additionally, `db:seed:remote` (line 16) points at **`staffnow-db-prod --remote`** and injects `admin@staffnow.gr` plus 8 fake demo users/businesses/jobs/conversations (`src/db/seed.sql`) with unusable `$argon2id$…placeholder_hash` passwords. One mistyped command puts demo data into production.

## HIGH

**6. Plan/paywall enforcement is client-side only**
- `checkSwipeLimit` (`middleware/subscription.ts:142`) is imported in `workers.ts:7` and `jobs.ts:6` but **never called** — `maxSwipesPerMonth` is not enforced anywhere (the only usage is the broken middleware in #3).
- Credit costs (`credits.ts:16-29`: `ai_shortlist: 3`, `ai_hiring_chat: 5`, `ai_cv_generate: 5`, …) are only deducted by `POST /credits/spend`, a **separate endpoint the client calls voluntarily**. `ai.ts:575 /shortlist/:jobId`, `ai.ts:712 /hiring-chat`, `workers.ts:1261 /ai/cv-generate` do not deduct anything. A client that simply skips the `/spend` call gets the feature for free.
- `workers.ts:1604,1630` hardcode `const cost = 0` for both boost types despite `boost_discover: 2` / `boost_application: 1`.

**7. IDOR + paywall bypass on AI shortlist endpoints**
`apps/api/src/routes/ai.ts:486-570` and `ai.ts:575-704`
- No ownership check on `:jobId` — any user can shortlist candidates for **any** business's job.
- The plan gate is `if (user.role === 'business' && !hasFeature(...))` (lines 493, 581, 306). A **worker** account skips the gate entirely and gets the full ranked candidate list including `expected_hourly_rate` / `expected_monthly_salary` / `profile_completeness` for every visible worker.

**8. Unauthenticated-by-ownership AI embedding writes**
`apps/api/src/routes/ai.ts:155-220`
`POST /ai/embed/worker/:id` and `/ai/embed/job/:id` are `requireAuth` only. Any user can overwrite `worker_profiles.embedding` / `job_listings.embedding` for anyone, and burn the Workers AI quota (10k neurons/day free tier) at will.

**9. Google OAuth bypasses 2FA, has no CSRF state, and doesn't check email verification**
`apps/api/src/routes/auth.ts:1326-1424`
- The callback signs a JWT directly (line 1414) without the `totp_secret && totp_enabled_at` check that `/login` performs (line 183). Any account with 2FA enabled — including admins — can be entered through Google with the password+TOTP step skipped.
- `state` carries only the role (line 1319), so there is no CSRF token: an attacker can force a victim's browser through a callback and log them into the attacker's account.
- `googleUser.verified_email` is never checked.
- No rate limiter on `/auth/google*`.

**10. Notification preferences are write-only — all opt-outs are ignored**
`apps/api/src/routes/notifications.ts:172-205` writes `notification_settings`; `apps/api/migrations/0054` creates it. `apps/api/src/lib/notify.ts` — the only dispatcher for push (`dispatchPush:96`) and email (`dispatchEmail:172`) — **never reads that table**. Confirmed by grep: `notification_settings` appears only in `notifications.ts`.
*Impact:* users who turn off `emailMatches` / `emailMessages` / `emailMarketing` / `pushMatches` / `pushMessages` keep receiving everything. The migration's own comment calls `email_marketing` out as the one that must work. Consent/GDPR exposure.

**11. Granular admin roles are decorative**
`apps/api/src/routes/admin.ts:1522` defines `ADMIN_ROLES = ['super','operations','moderation','support','finance','analytics']`; `0032_admin_roles.sql` adds the column. Grep confirms `admin_role` is only **stored and displayed** — never checked. Every one of the ~70 admin endpoints is gated solely by `requireRole('admin')`, so an `analytics` or `support` admin can issue Stripe refunds (`admin.ts:3581`), create other admins (`admin.ts:1542`), read every private conversation (`admin.ts:1065`), and confirm bank transfers (`admin.ts:3435`).

**12. Production bank IBAN is a placeholder**
`apps/api/src/lib/billing.ts:725` — `BANK_ACCOUNT = { iban: 'GR16 0260 0000 0000 0000 0000 000' } // placeholder — replace`. It is returned verbatim to paying customers by `POST /billing/manual-transfer` (`routes/billing.ts:956`) and `GET /billing/manual-transfer/:id` (line 972), with instructions to wire money there.
Also `lib/billing.ts:609-616`: `COMPANY.vat = '—'`, `doy = '—'`, `address = '—'`, embedded into every issued Τιμολόγιο/Απόδειξη (`renderInvoiceHtml:669-672`) — these are not valid Greek tax documents.

**13. Stripe checkout accepts unvalidated redirect URLs**
`apps/api/src/routes/billing.ts:803-804` passes the caller-supplied `body.successUrl` / `body.cancelUrl` straight into the Stripe session; `billing.ts:887` does the same for `returnUrl` in the portal session. Open redirect, laundered through `checkout.stripe.com` — ideal for phishing ("pay on StaffNow" → attacker page).
Also `checkout.session.completed` (`billing.ts:106`) never checks `session.payment_status === 'paid'`, so async payment methods can activate a subscription before the money settles.

**14. `POST /push/subscribe` is an SSRF primitive and allows subscription hijack**
`apps/api/src/routes/push.ts:21-50` stores an arbitrary user-supplied `endpoint` URL with no scheme/host allowlist; `lib/webpush.ts:193` then `fetch`es it (POST, from Cloudflare's egress) on every notification. Additionally `ON CONFLICT(endpoint) DO UPDATE SET user_id = excluded.user_id` (line 41) lets anyone who learns another user's endpoint re-point it and silence that user's push notifications.

**15. No tests for any route, middleware, or SQL**
Only three test files exist in the whole repo: `packages/validation/src/__tests__/auth.test.ts`, `packages/shared-utils/src/__tests__/format.test.ts`, `apps/api/src/lib/__tests__/totp.test.ts`. Zero coverage of auth middleware, IDOR checks, billing/webhook logic, or schema/query agreement — which is precisely why findings #3 and #4 are still live.

## MEDIUM

**16. `SELECT m.*, wp.*, bp.*` column collision returns wrong data**
`apps/api/src/routes/matches.ts:131-150` — `matches`, `worker_profiles` and `business_profiles` all have `id`, `created_at`, `updated_at`, `region`, `verified`, `description`. Last-wins in the result object, so `match.id` returned at line 246 is actually `bp.id` (a `bp_…` business-profile id), and `createdAt` is the business profile's. Also `m.industry`, `m.company_size`, `m.contact_name/email/phone`, `m.business_logo`, `m.worker_region` (lines 168-207) reference columns that exist nowhere, so the premium "contact reveal" hands back `undefined`. (Moot today because of the `worker_languages` 500 in #4, but both need fixing.)

**17. SQL built by string interpolation (3 sites)**
`jobs.ts:137-138` (`swiper_id = '${user.id}'`, `worker_id = '${user.id}'`), `workers.ts:501,597,598` (`business_id = '${user.id}'`, `swiper_id = '${user.id}'`). Not exploitable today because `generateId()` (`lib/id.ts`) emits `[a-z0-9]` only — but it is one ID-source change from injection, and `docs/SECURITY.md:14` already *claims* "`routes/jobs.ts` — parameterized `worker_id` binding", i.e. the doc says this was fixed and it wasn't.

**18. `PATCH /jobs/:id` has no schema validation**
`apps/api/src/routes/jobs.ts:493-501` — `updateJobSchema` is imported (line 3) and used for `POST /` via `zValidator`, but the PATCH handler reads raw `c.req.json()` and writes any allow-listed key straight through. Negative salaries, 10 MB titles, `positions: -5`, arbitrary `salary_type` all land in the DB.

**19. `branch_id` IDOR — branch impersonation**
`jobs.ts:302` (create) and `jobs.ts:540` (`branch_id` in `allowedFields`) accept `branch_id` with no check that the branch belongs to the caller. Since `jobs.ts:120-133` and `index.ts:462-464` render `COALESCE(br.name, …)`, `br.logo_url`, `br.cover_photo_url` from that join, a business can publish a job that displays a **competitor's** name, logo and cover photo.

**20. `GET /jobs/:id` leaks drafts and archived listings**
`apps/api/src/routes/jobs.ts:462-490` — no `status` filter and no ownership check. Any authenticated user can read any business's unpublished drafts by id.

**21. Business account email leaked to unmatched workers**
`apps/api/src/routes/interests.ts:28` — `GET /interests/received` selects `u.email as business_email` and returns it raw, for any business that merely liked the worker. `businesses.ts:415-418` deliberately hides that same field until there is an active match.

**22. `/video/create-room` is an unfixed stub — and `docs/SECURITY.md` knows it**
`apps/api/src/index.ts:306-314`: takes `conversationId`, never checks membership, returns a room name, persists nothing. `docs/SECURITY.md:44-46` lists exactly this as open. Real calls go through `routes/calls.ts`, so this is dead code that still answers.

**23. Non-atomic credit spend (race)**
`apps/api/src/routes/credits.ts:129-157` — read balance, then `UPDATE … balance = balance - ?`. Concurrent requests can both pass the check and drive the balance negative. Should be a single conditional `UPDATE … WHERE balance >= ?` and check `meta.changes`.

**24. HTML injection into outbound emails**
`apps/api/src/lib/email.ts:127,133,142` interpolate `heading`, `body` and `ctaUrl` without escaping. `title`/`body` are built from user-controlled data: sender display name (`conversations.ts:319-320`), worker `full_name` (`businesses.ts:537`, `workers.ts:857`), company name, and a 100-char message preview. A user can inject `<a href>` markup into a genuine StaffNow-branded email. (Contrast `lib/billing.ts:624 escapeHtml`, which does it correctly for invoices.) `docs/SECURITY.md:40-42` flags the adjacent admin-message case and it is likewise unfixed.

**25. Upload handler: attacker-controlled R2 key prefix, size checked after buffering**
`apps/api/src/routes/uploads.ts:187,232,326` — `category` comes straight from the form/body and is prefixed onto the R2 key with no sanitization. Since `lib/signed-url.ts:26` decides "protected" purely by the `verification/` prefix, whether an identity document is signature-gated or **world-readable and cached for a year** depends entirely on a client-supplied string.
Line 196 does `await file.arrayBuffer()` before the size check at line 224 — the whole body is buffered first. There is also no per-user rate limit or quota on uploads.

**26. `POST /uploads/presign` is non-functional and leaks R2 state**
`uploads.ts:290-351` creates a multipart upload and returns `uploadId` + a **read** URL — never a presigned upload URL, and there is no complete/abort endpoint. Every call leaks a dangling multipart upload that is billed until aborted. Documented in `docs/API.md:88` as working.

**27. `/calls` is fully exempt from rate limiting**
`apps/api/src/index.ts:82-92` skips the global limiter for `/calls`, and none of the 9 call routes adds one. `POST /calls/:id/candidates` (`calls.ts:472`) accepts 30 × 4 KB strings per request with unbounded repetition → cheap D1 write amplification. `GET /calls/ice` (`calls.ts:162`) mints fresh Cloudflare TURN credentials for any authenticated user on demand with no throttle.

**28. `/tasknow/geocode` and `/tasknow/reverse` are an open Nominatim proxy**
`apps/api/src/routes/tasknow.ts:397,475` — unauthenticated, forwarding arbitrary query strings to `nominatim.openstreetmap.org` under StaffNow's identifying User-Agent. Nominatim's usage policy prohibits this pattern; abuse gets the whole platform's geocoding blocked.

**29. Admin SSE auth token travels in the query string**
`apps/api/src/routes/admin.ts:3082,3206` — `?token=<JWT>` for `/admin/security/stream` and `/admin/analytics/stream`. Admin JWTs end up in Cloudflare access logs, browser history and any `Referer`. (The role and `sessionStillValid` checks themselves are correct.)

**30. Fabricated metric in the admin dashboard**
`apps/api/src/routes/admin.ts:203` — `dau: signupsSeries.map((v) => Math.max(1, v * 4))`, commented "DAU approximation (deterministic, based on signups)". It is presented as a real analytics series to the operator.

**31. `/stats/dashboard` swallows errors as success**
`apps/api/src/index.ts:352-355` — the catch returns `{ success: true, data: { …all zeros } }` with HTTP 200. A broken query silently renders "0 matches, 0 messages" instead of an error, indistinguishable from a genuinely empty account.

**32. Archiving a conversation archives it for both parties**
`apps/api/src/routes/conversations.ts:444-447` — `action: 'archive'` sets `matches.status = 'archived'`, which `POST /:id/messages` (line 261) then uses to block **both** users from sending. One side tidying their inbox silently mutes the other. (`action: 'restore'`, line 459, restores *all* matches between the pair, not just this one.)

**33. `DELETE /auth/me` has no re-authentication**
`apps/api/src/routes/auth.ts:343-357` permanently deletes the account (cascading to profiles, matches, messages, credits) on a bare authenticated DELETE — no password prompt, no confirmation token, no rate limit. Any XSS or borrowed session destroys the account irreversibly.

**34. `PATCH /auth/me/settings` accepts unvalidated `displayName` / `avatarUrl`**
`auth.ts:329-330` — no length cap, no type check beyond `!== undefined`, no URL validation. `display_name` is rendered as a sender name across conversations and emails (see #24); `avatar_url` is echoed into `<img src>` on the frontend and can point anywhere (tracking pixel / `javascript:`).

**35. Duplicate matches possible**
`matches` is `UNIQUE(worker_id, business_id, job_id)` (`0006`), and SQLite treats every NULL as distinct. `businesses.ts:584`, `workers.ts:930` and `interests.ts:265` all insert with `job_id` NULL, so concurrent requests (or `like` + `like-back` racing) create duplicate match+conversation pairs for the same pair of users. The constraint is only relied upon, never backed by a unique partial index.

**42. Monthly swipe window compares mixed date formats.** `middleware/subscription.ts:160-167` compares `monthStart.toISOString()` (`…T00:00:00.000Z`) against `swipes.created_at`, which is ISO for app inserts but `'YYYY-MM-DD HH:MM:SS'` for the column default (`0006`). Also `setDate(1); setHours(0,0,0,0)` uses the worker's UTC clock, not Europe/Athens — the reset lands at 02:00/03:00 local.

**43. Notification written before the action it announces.** `workers.ts:854-871` and `jobs.ts:1094-1111` insert the "X is interested in you" notification and fire push/email **before** the `swipes` row is written (lines 884 / 1120). If the insert fails, the recipient has already been told about an interest that does not exist.

**44. `POST /businesses/me/verify` accepts an arbitrary `document_url`.** `businesses.ts:238` stores whatever string is sent, with no check that it is an R2 key owned by the caller. An admin later opens it in the review UI — attacker-controlled URL rendered to a privileged reviewer.

**45. Unused/dead code.** `conversations.ts:225,267` — `attachmentUrl` and `messageType` are read from the body and then dropped; the `INSERT` at line 271 has no such columns, so message attachments are silently discarded. `credits.ts:139-148` returns HTTP 200 with `{ success: true, data: { success: false, insufficient: true } }` — a nested success flag the client must special-case.

**46. `GET /public/businesses` is 2N+1.** `index.ts:553-573` issues two queries per business inside a loop, up to 50 businesses, on an unauthenticated endpoint.

## What `guard.mjs` actually protects — and its real gaps

It is 1063 lines and 12 checks, each written after a specific production incident (`checkApiSurface`, `checkPermissionsPolicy`, `checkApiRoutes`, `checkNotificationBell`, `checkHeroPhotos`, `checkTaskNow`, `checkMigrationsWired`, `checkFavicons`, `checkVideoCalls`, `checkBoostVisible`, `checkTaskNowPhoneReal`, `checkLocationGuideNotAuto`, plus `--live` at 1003-1033). **It is entirely static string/regex matching on source. It would not catch:**
1. **Any runtime behaviour.** Every finding in Part A passed guard — because `api.matches.list()` *exists*, and guard only asks whether the method exists, never what shape it returns (`guard.mjs:96` matches `api.<group>.<method>(`, nothing more).
2. **A method that exists but is never called** — finding #1. Guard checks used→defined, never defined→used.
